# PCB photo → BOM → cost: 360 review (12 Oct 2026)

The board is the 360° camera board (TI DS90UB935-Q1 FPD-Link III serializer, image sensor, 20 × 20 mm, 8 layers). It
is built in China at 250,000 boards a year. The review covers four things:

- **Code:** two independent traces of every stage, from photo intake to the exported reports.
- **Live runs:** a real server and a real browser, with a recorder on every model request.
- **Hand check:** every figure recomputed by hand.
- **Exports:** every line of the PDF and Excel reports read.

## 0. What this run is — and is not

| | |
|---|---|
| **Photos** | The engineer's own photos of the board (top, sensor side, 341 × 334 px; bottom, serializer side, 680 × 670 px), the BOM table picture (1774 × 810 px) and the board data sheet, all as uploaded on 6 Oct. A second run used eight full-size 4032 × 3024 photos to prove that eight photos all reach the model. |
| **The model's reading** | **Replayed, not live.** There is no Anthropic key in this environment, and none was taken from the chat. The model's answers are the ones it gave for these photos on 6 Oct (`e2e/fixtures/pcb-camera-replies.json`), served by `e2e/pcb-stand-in.mjs`. Everything after the model — every request the server builds, every price, every £ — is the real code running. |
| **Live distributor prices** | Not called. No Nexar / Octopart or RS key is set. Prices come from the offline catalogue (`server/data/pcb-component-catalogue.json`, 1,217 parts) and the tool's class tables. **Nothing searches the internet.** |
| **Accuracy** | Not measured. There is one real price: the engineer's £17.00 for this board, against the tool's £16.13 (−5 %). One point is not an accuracy figure. No labelled board exists in `tests/fixtures/pcb-boards/`, so how well the model reads photos is not measured either. |

## 1. Does the tool look at every photo? — Yes (proven)

The recorder (`REQUEST_LOG` in `e2e/pcb-stand-in.mjs`) captures every request the server sends to the model. With eight
photos uploaded, each of the five vision stages received **all eight images** (7.9 MB of base64):

| # | Stage | Model | Images | Output |
|---|---|---|---|---|
| 1 | Board-type classifier | Haiku 4.5 | 8 | 512 tokens |
| 2 | ASIL classifier (automotive boards only) | Haiku 4.5 | 8 | 768 |
| 3 | Chip-marking OCR | Sonnet 5.5 | 8 | 4,096 → **8,192** (fix I3) |
| 4 | BOM picture transcription (schema has no price field) | Sonnet 5.5 | the BOM picture only | 16,000, streamed |
| 5 | Parts list (schema has no cost fields) | Sonnet 5.5 (Opus 5.5 under Deep analysis) | 8 | 32,000, streamed |
| 6 | Second look at ICs with no part number (here: the image sensor) | Opus 5.5 | 8 | 2,048 |
| 7 | Cost commentary (after Calculate) | Haiku 4.5 | none | 420 |

Every multi-photo prompt opens: *"You are given N views of the SAME board … a component visible in ANY view counts
once … do not miss parts that appear only on one side."* Each image is labelled with its slot (Top side, Bottom side,
Close-up 1 …).

What the code does **not** do: record which photo a part was seen in. The parts-list schema has no "photo" or "side"
field, so "every part was found" cannot be proven photo by photo. Duplicates across photos are merged by designator
(`consolidateBom`).

## 3. The cost, figure by figure (China, 250,000 a year)

| Bucket | £ / board | How |
|---|---|---|
| Components | 13.73 | the 11 lines above |
| EMS material burden 5 % | 0.69 | `materialBurdenFor` (≥ 100k boards) |
| Bare board | 0.38 | base 0.01 + layers 0.03 + vias 0.22 + impedance 0.01 + automotive fab 0.12 (IATF, class 3) |
| Assembly & test | 0.62 | SMT 0.26 + AOI / X-ray / ICT 0.23 + automotive assembly 0.13 |
| Energy, packaging, yield | 0.13 | |
| Freight + UK duty | 0.58 | sea 0.01 + duty 3.7 % × (14.42 + 0.38 + 0.62) = 0.57 |
| **Delivered UK** | **16.13** | Calculate gives the same £16.13 |

ASIL: the classifier said ASIL-C, with a *radar* rationale on a camera board. The guard withheld the rationale and
costed ASIL-B, because no safety PMIC / SBC is named on the BOM. The country table runs from China £16.13, Vietnam
£16.39 and India £16.38 up to the UK £21.15 and Japan £21.47.

## 4. Defects found and fixed (each with a test)

Intake (`server/routes/pcb.ts`, `src/ui/main.ts`):

| # | Defect | Fix |
|---|---|---|
| I1 | Close-ups were resized by their position in the list, not by slot: with the bottom slot empty, Close-up 1 went at 1600 px instead of 2576 px | resized by slot, as /reanalyze already did |
| I2 | A HEIC / GIF photo, a ninth photo or a file over 20 MB failed the **whole** analysis with HTTP 500, shown in production as "Internal server error" | refused on the screen; a refused upload is a 400 with its reason |
| I3 | An OCR reply cut off at 4,096 tokens lost **every** marking ("OCR failed") | the complete markings are kept (`pcb-ocr-parse.ts`), with an `OCR_PARTIAL` warning; the budget is now 8,192 |
| I4 | A run whose classifier or OCR failed said "run again" — and the cache replayed it for 30 days | such runs are no longer cached (`isCacheableRun`) |
| I5 | When the request budget dropped photos, the model was still told "you are given 8 views", and the warning named the wrong photos ("Additional 1") | the count and labels are those of the photos actually sent |
| I6 | A cut-off parts list dropped the board spec, so a 100 × 80 mm, 4-layer default priced the fab silently | the spec is kept when it is complete; otherwise the warning says size and layers are defaults |
| I7 | With more than 12 unread ICs, the second look was skipped silently | warning `SECOND_LOOK_SKIPPED` |
| I8 | The BOM picture went up raw (a phone photo over 20 MB failed the analysis) | resized to 2576 px, like a close-up |

Pricing (`runStage4`, `pcb-class-pricing.ts`, `pcb-live-pricing.ts`):

| # | Defect | Fix |
|---|---|---|
| P1 | **An engineer's price correction was lost on the next re-price** (country, quantity, form edit, Fetch Live Prices). Re-pricing restarts from the BOM as first read and sends no corrections. On the radar board, J1 corrected to £0.50 went back to £5.38 | corrections are kept on the analysis (`userCorrections`) and applied on every re-price |
| P2 | Editing only a quantity froze the tool's price as the engineer's and took the line out of "to verify" | `priceEdited: false` changes the count and leaves the price to the tool |
| P3 | Placements were counted before corrections, so a corrected quantity did not move the assembly cost | placements and joints are recounted after corrections |
| P4 | `aiFirstPass` (the model's own figures, kept for audit) held the **tool's** figures, so the BOM-total check compared the sum with itself and never fired | the model's figures are captured before Stage 4 writes its own |
| P5 | On a board classified "general", the model's word "automotive" or its flag moved lines to AEC-Q prices (+19 % BOM in the trace) | only an automotive board, or the user's own BOM / edit, selects AEC-Q |
| P6 | Board figures no photo can show (layers, vias, HDI, ICT time) were priced with no flag | listed with the £ each drives (`BOARD_FIGURES_ESTIMATED`) |
| P7 | The model's IC class beat the line's own package ("QFN-16" typed `ic_bga` was priced as a BGA, £14.34 v £3.19) | the stated package wins; imagers stay BGA-class |
| P8 | Live pricing: four variants per part under a cap of 20 reached only **5** parts, and a bare trailing "Q" was stripped, so a part whose code ends in Q matched its sibling | originals are queried first; results map back to the part they were made from |
| P9 | An unknown country was priced as China while the response named the country asked for | warning `COUNTRY_UNKNOWN` |
| P12 | **Outer copper typed from the data sheet was struck back to 1 oz** by the evidence gate (found in the live run) | a typed copper weight carries user evidence |

Labels on the screen and in the reports:

| # | Was | Now |
|---|---|---|
| L1 | "→ £14.42 in China … after the country's component sourcing factor" | "with the EMS material burden". There has been no country factor since F13; the gap is the 5 % burden |
| L2 | Calculate's report scaled every BOM line × 1.05 and called it a "sourcing factor" | lines at the analysis price, with the burden as its own line |
| L3 | "ICs identified: N" (the count of OCR markings) | "Chip markings read" |
| L4 | AI commentary: "Unnamed Part … manufactured in United Kingdom … Material 96 %", asked to compare against "benchmark" | the PCB's own name, country and buckets; told to quote no benchmark or number it was not given |
| L5 | Class tables labelled "at 100K" while the code reads them as ~10k reel prices | labels say ~10k (`TABLE_BASIS_QTY`); the prompt still says 100K, but the model's price is never used |
| L6 | "Components follow each country's sourcing index" (PDF) | "one global market … plus the EMS material burden" |

## 5. Open — stated, not fixed

| Item | Why |
|---|---|
| Photo-reading accuracy is unmeasured | No labelled board. The top photo here is 341 × 334 px: too small to read any marking. The part numbers came from the BOM picture, not the photos. |
| No per-photo attribution | The schema has no photo or side field; "every part found" cannot be proven photo by photo |
| Second reflow side not costed | No sourced volume figure (stencil, set-up, pass) |
| Through-vias (115) and ICT time (60 s) are the model's estimates | Now flagged; only Gerbers / drill files or the engineer can set them |
| Inner copper cannot be typed (the form has outer copper only) | The data sheet's 70 µm on layers 2 and 7 is not costed; on this 4 cm² board the effect is under £0.01 |
| A figure re-typed unchanged (e.g. 20 × 20) does not mark it "measured" | The form counts only changed fields as edits |
| Duplicates across photos are merged by designator; identical lines with no designators are merged at the larger quantity, not the sum | By design (a part seen in two views must count once); flagged `qtyUnverified` |
| The OCR "evidence" for a part number is itself a model reading | Two model calls agreeing, not a deterministic read |
| Prompts still say "100K" | Prompt text only; changing it changes replies |
| China rates, 3.7 % duty, via adders, automotive premium % | Engineering figures from the rate tables; not re-sourced in this review |

## 6. How to reproduce

```bash
cd calculator && npm run build
# eight generated 4032×3024 photos (every image reaches every vision stage):
PLAYWRIGHT_CHROMIUM_PATH=/opt/pw-browsers/chromium CV_OUT=out npx tsx e2e/pcb-camera-review.ts
# the engineer's photos + BOM picture, then the data sheet's copper typed and re-priced:
CV_PHOTO_FILES=top.jpg,bottom.jpg CV_BOM_FILE=bom.jpg CV_EDITS='{"pcbf-outer-cu":"2"}' CV_OUT=out-real \
  PLAYWRIGHT_CHROMIUM_PATH=/opt/pw-browsers/chromium npx tsx e2e/pcb-camera-review.ts
npm test -- pcb-360-review
```

`out/request-log.jsonl` lists every model request (model, tokens, images); `analysis.json` holds the screen's own
response; `pcb-report.pdf`, `pcb-report.xlsx` and `report.pdf` are the exports.
